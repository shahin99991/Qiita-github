## デモ手順（実機）

### デモ① README 更新 → PR 自動作成（目安: 2分）

**目的**: メンションするだけでタスク分解 → PR 作成まで完結することを見せる

**手順**:

1. Teams のデモ用スレッドを開く
2. 以下を入力して送信：

```
@GitHub README を最新の構成に更新して
```

3. Copilot の応答を待つ（タスク分解の進捗バーが出る）
4. 完了したら GitHub 側の PR を開いて見せる

**見せるポイント**:

- タスク分解の進捗バー（0/4 → 4/4）
- PR の説明文に「Created from a Microsoft Teams conversation」と自動で入る
- モデルバッジ（初期は `gpt-5.6-sol` など）

**トーク例**:

🎬 **開始時**: 「まずは軽いところから。『README を最新の構成に更新して』とだけ投げます。これだけです」

⏳ **待ち時間**: 「ほら、もうタスク分解が始まりました。『リポジトリの現状構成を確認』『既存 README の確認』『更新』『コミット・プッシュ』って 4 ステップに分かれてます。これ、自分でやると地味に面倒なやつです」

✅ **結果**: 「できました。PR が自動で作られてます。しかも説明文に『Created from a Microsoft Teams conversation』って入ってる。会話から生まれたことがちゃんと残るんです」

🔗 **つなぎ**: 「会議中に出たアクションアイテムをその場で投げると、会議が終わる頃には PR ができてる、という世界観です。次はもっと実践的なやついきます」

### デモ② エラー修正（トレースバック → PR）（目安: 4分）⭐ 山場

**目的**: エラーのスクショ/テキストを貼るだけで修正 PR まで作ってもらえることを見せる

**手順**:

1. 事前に撮影した `KeyError: 'WatchEvent'`（または `KeyError: 'ReleaseEvent'`）のトレースバック画像を Teams に**インラインで貼り付ける**
2. 以下を入力して送信：

```
@GitHub このエラー直して
```

3. Copilot の応答を待つ

**想定される流れ（パターンA: スムーズにいく場合）**:

- Copilot が `src/notifier.py` の `MessageFormatter.format` メソッドを特定
- 修正内容（`EVENT_EMOJI` に `ReleaseEvent` 追加・`.get()` でフォールバック・デフォルト絵文字 🔔 追加）を説明
- PR を自動作成

**想定される流れ（パターンB: リポジトリ不一致が出る場合）⭐ これが一番美味しい**:

- Copilot が「このスレッドは別のリポジトリに接続されていますが、切り替えますか？」と検出
- 「切り替えて」と返信
- 即座に切り替えて修正完走

**画像解析が失敗した場合（パターンC）**:

- 「I couldn't read these images. Try attaching them again.」と出る
- **もう一度画像を添付し直す**（リトライ）
- 成功したら「再送で読めました！エラーが出たらリトライがコツです」と説明

**見せるポイント**:

- トレースバックの行レベル特定（`src/notifier.py` の 86行目 `EVENT_EMOJI[event.event_type]`）
- リポジトリ不一致を自分で検出して確認を取ってくる賢さ
- 修正報告が「原因・修正内容・動作確認」までフルセット
- GitHub 側の PR を開いて「Created from a Microsoft Teams conversation」を見せる

**トーク例**:

🎬 **開始時**: 「このボット、実は4つもバグを仕込んでるんです。Copilot が全部見つけてくれるか、見てみましょう。エラーのスクショを貼って『このエラー直して』とだけ言います」

⏳ **待ち時間（パターンA）**: 「裏でクラウドサンドボックスが動いてます。トレースバックを読んで、`src/notifier.py` のどこが悪いか探ってるはず…」

⏳ **待ち時間（パターンB・不一致検出）**: 「おっと、来ました。『このスレッドは別のリポジトリに接続されていますが、切り替えますか？』って。**自分で設定ミスを検出して確認を取ってくる**んです。これ、9/25 アプデの信頼性改善が効いてる場面です。『切り替えて』と返します」

⏳ **待ち時間（パターンC・画像失敗）**: 「あ、『I couldn't read these images』って失敗しました（笑）。でも Copilot の言う通り**もう一度添付し直す**と…ほら、読めました！エラーが出たらリトライがコツです」

✅ **結果**: 「修正完了しました。原因・修正内容・動作確認までフルセットで報告してくれます。`EVENT_EMOJI` に `ReleaseEvent` 追加して、`.get()` でフォールバック入れて、デフォルト絵文字 🔔 も追加。しかも『Created from a Microsoft Teams conversation』つき。仕事が丁寧すぎる」

🔗 **つなぎ**: 「勝手に間違ったリポジトリを探しに行かず、状況を説明して確認を取ってくる。これ、結構感動しました。次は会話の流れを読むやついきます」

### デモ③ 転送メッセージ → Issue 作成（目安: 2分）

**目的**: 会話のコンテキスト（転送メッセージ）を読んで Issue を自動生成することを見せる

**手順**:

1. 別チャネルに `docs/meeting-notes.md` の内容（`ReleaseEvent` 対応・エラーで落ちないでほしい・レート制限対策・レビュアーメンション機能など）を会話として用意しておく
2. その1件を「共有」→ 転送でデモ用スレッドに送る
3. 以下を入力して送信：

```
@GitHub この内容を踏まえて Issue を立てて
```

4. Copilot の応答を待つ

**見せるポイント**:

- 転送元の会話内容を読んで「内容・背景・対応」の3段構成の Issue を自動生成
- 「重複する既存 Issue はありませんでした」の報告
- 要件が複数ある場合、子 Issue に分割してくれる可能性もある

**トーク例**:

🎬 **開始時**: 「次は転送メッセージです。別チャネルでこんな話をしてたんですが…（会議メモの内容を見せる）これをそのまま転送して『この内容を踏まえて Issue を立てて』とだけ言います」

⏳ **待ち時間**: 「転送元の会話を読んでるはずです。`ReleaseEvent` 対応・エラーで落ちないでほしい・レート制限対策・レビュアーメンション…要件が4つもあるんですが、どう整理してくるか」

✅ **結果**: 「来ました。『内容・背景・対応』の3段構成の Issue が自動生成されました。しかも『重複する既存 Issue はありませんでした』ってちゃんとチェックしてる。要件が多い場合は子 Issue に分割してくれることもあります」

🔗 **つなぎ**: 「別チャネルの議論をそのまま転送して Issue 化、が1メッセージで済みます。情報があちこちに散らばる問題の解消に直結します。次はモデル切り替えいきます」

---

### デモ④ モデル切り替え（目安: 1.5分）

**目的**: セッション内でモデルを切り替えられることを見せる

**手順**:

1. 以下を入力して送信：

```
@GitHub 今使っているモデルは？ Change可能なモデル一覧も出して
```

2. モデル選択プロンプトが表示されたら、一覧を開く
3. `MAI-Code-1.1-Flash` を選択して Submit

**見せるポイント**:

- モデル選択プロンプトが「このメッセージはあなただけに表示されます」（自分にだけ見える）
- ラインナップの豊富さ（Auto / Claude Sonnet 5 / Claude Opus 4.8 / GPT-5.5 / MAI-Code-1.1-Flash / Kimi K3 など）

**トーク例**:

🎬 **開始時**: 「ここでちょっと寄り道。『今使っているモデルは？ Change可能なモデル一覧も出して』と聞いてみます」

⏳ **待ち時間**: 「自分にだけ見えるプロンプトが出ました。『このメッセージはあなただけに表示されます』って書いてある。一覧を開くと…」

✅ **結果**: 「Auto・Claude Sonnet 5・Claude Opus 4.8・GPT-5.5・MAI-Code-1.1-Flash・Kimi K3…マルチベンダーの模型店と化してます。今回は `MAI-Code-1.1-Flash` に切り替えてみます」

🔗 **つなぎ**: 「調査フェーズは速いモデル、実装は強いモデル、みたいな使い分けがチャットの中で完結します。最後に、この切り替えがちゃんと維持されてるか確認します」

---

### デモ⑤ 重複 Issue 検出＋モデル維持の証明（目安: 0.5分）

**目的**: 類似 Issue チェックと、切り替えたモデルが会話中維持されることを同時に見せる

**手順**:

1. 以下を入力して送信：

```
@GitHub 「ReleaseEvent に対応してほしい」の Issue を作成して
```

2. Copilot の応答を待つ

**見せるポイント**:

- 「同内容の Issue はすでに作成済みです。重複を避けるため、新規作成はせず既存の Issue を使ってください」とストップ
- **右下のモデルバッジが `MAI-Code-1.1-Flash` のまま** → 切り替えが会話中維持されている証拠

**トーク例**:

🎬 **開始時**: 「最後の検証です。さっき作った Issue とほぼ同じ内容をわざと依頼します。『ReleaseEvent に対応してほしい』の Issue を作成して、と」

⏳ **待ち時間**: 「どう返ってくるか…」

✅ **結果**: 「来ました。『同内容の Issue はすでに作成済みです。重複を避けるため、新規作成はせず既存の Issue を使ってください』。重複乱立防止、本当に効いてます！そしてここ、注目なんですが――右下のモデルバッジ、**`MAI-Code-1.1-Flash` のまま**なんです。さっき切り替えたモデルが、会話の後半でもちゃんと維持されている。changelog の『keep that choice throughout the conversation』が、スクショ上で確認できた瞬間です！」

🔗 **つなぎ**: 「重複検出とモデル維持、2つ同時に確認できました。デモは以上です。ここからは学びと注意点を整理します」

## デモのリスク対策

| リスク                                                               | 対策                                                                                                                                             |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Copilot の応答が遅い（30秒以上無言になる）                           | 「裏でクラウドサンドボックスが動いてるので、これが非同期の良さです」と説明しながら待つ。それでも来なければデモ①の結果（事前に作った PR）を見せる |
| 画像解析がまた失敗する                                               | 「前も失敗したんですよね〜」と笑いに変えて、再送で成功する流れをそのまま見せる（これはこれで美味しい）                                           |
| リポジトリ不一致が出ない（最初から正しく設定されている）             | 「本来ならここで不一致を検出してくれるんですが、今日はちゃんと設定されてますね（笑）」と言って、記事のスクショ（img-10）を見せる                 |
| 時間が押す                                                           | デモ④⑤を飛ばしてスライドの画像で済ませる（デモ①②③が核心）                                                                                        |
| ネットワーク不調                                                     | 記事のスクショをスライドに全枚挟んでおき、「画像で追います」と切り替え                                                                           |
| デモ用リポジトリの状態が変わっている（バグ修正 PR がマージ済みなど） | 別タスクに切り替える（例: `@GitHub tests/ を充実させて`、`@GitHub ReleaseEvent に対応して`、`@GitHub Webhook 送信にレート制限対策を入れて`）     |

- コンテキスト読解は本物
- リポジトリ不一致の検出と対話での復帰が賢い
- モデル切替が会話中維持される

⚠️ 注意点:

- 画像解析は初回失敗することがある → 再送で成功する
- パブリックプレビューは Business/Enterprise 限定
- 段階ロールアウト中の機能がある

### 活用アイデア

**トーク例**: 「じゃあ実際どう使うか、です。私が思う一番の活かし方は、**会議中にアクションアイテムをその場でエージェントに投げる**ことです。会議が終わる頃には調査が終わってる。あとはエラーのスクショをチャネルに貼って『これ直して』。別チャネルの要件議論を転送して Issue 化。調査は速いモデル、実装は強いモデル、と会話の中で使い分けるのもアリです。あと地味に嬉しいのが、**非エンジニアメンバーも Issue 作成に参加できる**こと。コードが書けなくても、要件を伝えれば Issue が立つんです」

- 調査は速いモデル、実装は強いモデル、と会話の中で使い分け
- 非エンジニアメンバーも Issue 作成に参加できる
